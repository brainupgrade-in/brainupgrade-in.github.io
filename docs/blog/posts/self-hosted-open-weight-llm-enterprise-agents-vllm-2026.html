The Enterprise Imperative for Self-Hosted Agents

For many enterprises, especially in regulated sectors such as banking, keeping sensitive data inside their own infrastructure is a hard requirement, and that rules out sending it to a public API. The solution is self-hosted open-weight models. However, raw model weights are not enough. You need a robust inference engine that handles concurrency, batching, and complex agentic workflows. Enter vLLM.

vLLM serves an OpenAI-compatible API, which is critical for enterprise integration. Most agentic frameworks, from LangChain to custom Go-based microservices, expect a standard OpenAI-style endpoint. By using vLLM, you bridge the gap between open-source innovation and enterprise infrastructure. This approach allows you to maintain control over your data while leveraging the latest open-weight architectures like gpt-oss-120b and Qwen3-30B-A3B.

Architecting for Tool Calling and Function Execution

Agentic workflows are useless without the ability to interact with external systems. Tool calling is the mechanism by which an LLM decides to call a function, such as querying a database or updating a CRM. In a self-hosted environment, this must be deterministic and secure.

vLLM supports tool_choice modes including auto, required, a named function, and none. A named function call is guaranteed to be parsable, though it is not guaranteed to be a good call. This distinction is vital for enterprise architects: you must validate the output before execution. To enable this, you must start vLLM with --enable-auto-tool-choice and specify a --tool-call-parser matched to the model. For example, you use hermes for Qwen2.5, qwen3_xml for Qwen3-Coder, openai for gpt-oss, and llama3_json for Llama 3.1/3.2.

This configuration ensures that the model’s output is structured correctly for your parser. In a payment or settlement system, this precision is non-negotiable: a malformed or wrong tool call must never reach your settlement logic.

Selecting the Right Open-Weight Models for 2026

Not all open-weight models are created equal for enterprise agents. You need models that balance parameter count, activation efficiency, and context length. Two models stand out for their specific architectural advantages.

gpt-oss-120b and gpt-oss-20b by OpenAI

OpenAI has released its open-weight models under the Apache 2.0 license, a significant move for the ecosystem. The gpt-oss-120b model has 117B total parameters with 5.1B active parameters. This mixture-of-experts architecture allows it to fit on a single 80GB GPU, which is a massive cost advantage for inference. The smaller gpt-oss-20b, with 21B total and 3.6B active parameters, runs within 16GB of VRAM. Both models support function calling and structured outputs. However, they must be used with the harmony response format. This format requirement is a technical constraint you must account for in your agent’s prompt engineering and post-processing layers.

Qwen3-30B-A3B by Qwen

For scenarios requiring deeper context, Qwen3-30B-A3B offers a native 32,768-token context window, expandable to 131,072 tokens with YaRN. It has 30.5B total parameters with only 3.3B activated, making it highly efficient. A key feature is the enable_thinking switch, which turns its thinking mode off. This is useful when you need low-latency responses for simple agent tasks, rather than the deeper reasoning required for complex analysis. Like gpt-oss, it is Apache 2.0 licensed, which permits commercial use.

Infrastructure and Security Considerations

Deploying these models on Kubernetes requires careful resource management. You are running large language models, which are memory-bound. You must ensure that your GPU nodes have sufficient VRAM and that your pod resource requests match the model’s footprint. For gpt-oss-120b, a single 80GB GPU is the baseline. For multi-GPU setups, you must configure tensor parallelism correctly in vLLM.

Security is paramount. Since you are hosting the model, you are also hosting the inference endpoint. This means you must implement authentication, rate limiting, and input validation. The OpenAI-compatible API provided by vLLM is a standard entry point, but you must wrap it with an API gateway that enforces enterprise security policies. This includes validating tool calls against a whitelist of allowed functions. As noted in vLLM’s official documentation on tool calling, the parser configuration is critical for ensuring that the model’s output is correctly interpreted by your system.

Practical Deployment Patterns

When deploying these models, consider the following patterns:

  • Single-GPU Deployment: Ideal for gpt-oss-20b or Qwen3-30B-A3B in low-traffic scenarios. This simplifies orchestration and reduces infrastructure complexity.
  • Multi-GPU Sharding: Required for gpt-oss-120b if you need higher throughput. This involves configuring tensor parallelism and ensuring low-latency interconnects between GPUs.
  • Model-as-a-Service: Deploy vLLM as a Kubernetes service with horizontal pod autoscaling based on queue length. This allows you to handle bursty traffic typical of agentic workflows.

Remember that tool calling is just one part of the equation. You must also handle structured outputs. For gpt-oss models, this means adhering to the harmony response format. For Qwen3, you may use JSON schemas or other structured formats depending on your parser configuration. The key is consistency. Your agent framework must be able to parse the model’s output reliably.

Frequently Asked Questions

What is the minimum GPU requirement for gpt-oss-120b?

gpt-oss-120b has 117B total parameters and 5.1B active parameters. It is designed to fit on a single 80GB GPU. This makes it accessible for enterprise deployments that may not have large GPU clusters.

Does vLLM support tool calling for all open-weight models?

vLLM supports tool calling, but it requires specific configuration. You must use --enable-auto-tool-choice and a --tool-call-parser matched to the model. For example, use openai for gpt-oss and qwen3_xml for Qwen3-Coder. Not all models may have a pre-configured parser, so you may need to verify compatibility.

How does Qwen3-30B-A3B handle context length?

Qwen3-30B-A3B has a native 32,768-token context window. It can be extended to 131,072 tokens using YaRN. This makes it suitable for agents that need to process large documents or long conversation histories.

Are gpt-oss models licensed for commercial use?

Yes, gpt-oss-120b and gpt-oss-20b are released under the Apache 2.0 license. This allows for commercial use, modification, and distribution. Separately from the license, both models must be used with the harmony response format.
