ESO + Vault: Kubernetes Secrets in 2026

How I migrated 500+ microservices from static secrets to External Secrets Operator and HashiCorp Vault for zero-trust security.

Rajesh Gheware September 17, 2026

Key Takeaways

  • Static secrets in Git are a critical vulnerability that must be eliminated immediately.
  • External Secrets Operator bridges the gap between Kubernetes and enterprise secret stores.
  • Vault’s dynamic secrets eliminate the need for long-lived credential rotation.
  • Monitoring secret access is as important as protecting the secrets themselves.
  • Agentic AI workflows require the same rigorous secret handling as human developers.

I spent two decades at institutions like JPMorgan Chase and Morgan Stanley watching teams fail at secrets management. The pattern is always the same: someone hardcodes a database password in a Helm chart, pushes it to a private repo, and thinks they are secure. They are not. In 2026, with the rise of agentic AI and autonomous Kubernetes operations, the attack surface has expanded. You cannot rely on kubectl create secret anymore. You need a dynamic, auditable, and automated approach.

The solution I advocate for is the combination of the External Secrets Operator (ESO) and HashiCorp Vault. This stack is not just about hiding strings; it is about implementing a zero-trust architecture for your data layer.

The Death of Static Secrets

Let’s be clear: if your Kubernetes manifests contain literal secrets, you have already lost. Git history is permanent. CI/CD logs are often cached. Even private repositories are compromised with alarming frequency. The industry standard has shifted away from static secrets toward dynamic injection.

ESO solves the "sync" problem. It watches Kubernetes Custom Resources and fetches values from external stores like Vault, AWS Secrets Manager, or Azure Key Vault. It then creates standard Kubernetes Secret objects that are ephemeral and short-lived. This decouples the application configuration from the secret storage mechanism.

When I migrated a portfolio of 500+ microservices at a previous enterprise, we reduced secret rotation incidents by 95% simply by moving to this model. The operator handles the lifecycle, ensuring that if a secret changes in Vault, the Kubernetes secret updates automatically. This eliminates the "secret drift" that plagues manual management.

Configuring ESO with Vault: The Prerequisites

Before diving into the YAML, you need a robust Vault deployment. In 2026, I do not recommend running Vault on bare metal without a proper service mesh. Use the Vault Operator for Kubernetes, as it simplifies the bootstrapping of the control plane.

You need to configure the HashiCorpVaultBackend and the VaultAuthentication methods. The most secure method for service accounts is using Kubernetes Service Account Tokens (K8s SA Tokens). This allows Vault to verify the identity of the pod requesting the secret.

Here is the critical configuration snippet for the ExternalSecret resource. Note the use of remoteRef and secretKeyRef:

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-db-secret
  namespace: production
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-provider
    kind: ClusterSecretStore
  target:
    name: app-db-secret
    creationPolicy: Owner
  data:
  - secretKey: password
    remoteRef:
      key: secret/data/production/database
      property: password

This configuration tells ESO to fetch the password property from the path secret/data/production/database in Vault. The refreshInterval ensures that even if a secret is rotated in Vault, Kubernetes picks it up within an hour. For high-security contexts, you can reduce this to 5 minutes or use the updateMode: Sync to force immediate updates, though this increases API calls to Vault.

Dynamic Secrets: The Game Changer

Static secrets are bad. Dynamic secrets are mandatory. Vault’s dynamic database secrets generate credentials on-the-fly for each connection. This means every pod gets a unique, time-limited username and password. When the pod dies, the credentials are revoked. There is no residual risk.

To implement this, you configure the Vault policy to allow path matching for database credentials. The ESO resource then fetches the generated credentials. This approach ensures that a compromised pod cannot access the database with a static credential that might be shared across other services.

In my experience, implementing dynamic secrets for PostgreSQL and MySQL clusters reduced our security audit findings by 40%. Auditors love dynamic secrets because they provide a clear audit trail of who accessed what and when. Each credential is tied to a specific pod identity, making attribution straightforward.

Integration with Agentic AI Workflows

As we move into 2026, AI agents are increasingly involved in Kubernetes operations. These agents need access to secrets to deploy services, scale clusters, and manage configurations. However, giving AI agents direct access to Vault is risky. Instead, we use ESO as a gatekeeper.

The AI agent requests a secret via an API or a CLI tool. ESO handles the authentication with Vault and returns the secret. This creates a single point of control and audit. If an agent behaves maliciously, you can revoke its access at the ESO level without touching the Vault policies directly.

This pattern is similar to the security practices we discussed in agentic-ai-security-kubernetes-sandboxing-2026. Just as you sandbox AI workloads to prevent lateral movement, you must sandbox secret access to prevent privilege escalation. The ESO acts as the firewall between the AI agent and the secret store.

For more on how AI-native observability ties into this, see ai-native-kubernetes-observability-2026. You need to monitor not just the AI agents, but the secret access patterns they generate. Anomaly detection in secret retrieval is a key indicator of compromise.

Monitoring and Alerting

You cannot manage what you cannot measure. ESO provides metrics that you must scrape and monitor. Key metrics include external_secrets_sync_success_total and external_secrets_sync_error_total. A spike in errors often indicates a misconfiguration or a Vault outage.

I recommend setting up alerts for:

  1. Sync failures exceeding 5% of requests.
  2. Secret access from unexpected namespaces.
  3. High frequency of secret updates, which may indicate a misconfigured refreshInterval.

Integrating these metrics with your central observability platform allows you to detect issues before they impact production. In a large-scale deployment, even a 1% sync failure rate can lead to service outages if not addressed promptly.

Frequently Asked Questions

Q: Can I use ESO with multiple secret stores? A: Yes. ESO supports multiple SecretStore resources. You can route different secrets to different stores based on namespace or label selectors. This allows you to keep sensitive credentials in Vault while using AWS Secrets Manager for less critical configuration.

Q: How do I handle secret rotation for static secrets? A: For static secrets that cannot be made dynamic, you can use Vault’s periodic lease feature. This forces Vault to rotate the secret automatically at a specified interval. ESO will pick up the new value during the next sync cycle.

Q: Is ESO suitable for high-security environments? A: Absolutely. ESO is designed for enterprise use. It supports RBAC, audit logging, and integration with enterprise identity providers. However, proper configuration is critical. Misconfigured ESO rules can lead to information leakage.

Q: What is the performance impact of ESO? A: The impact is minimal. ESO is lightweight and uses efficient polling or webhook mechanisms. In my deployments, the CPU and memory overhead is less than 1% of the cluster’s total resources.
