Policy-as-Code for Agent Actions: OPA, Gatekeeper, Kyverno

How to enforce safety and compliance on LLM tool calls using OPA, while keeping cluster governance separate.

Rajesh Gheware November 11, 2026

Key Takeaways

  • OPA evaluates LLM tool calls before execution, decoupling agent logic from cluster governance.
  • Kyverno and Gatekeeper manage Kubernetes resource lifecycle, not external agent actions.
  • The Model Context Protocol requires host-level enforcement for tool consent and safety.
  • Use OPA’s general-purpose JSON evaluation for structured agent decision-making.
  • Separate observability and cost attribution from policy enforcement for clearer audits.

The Boundary Between Agent Runtime and Cluster Governance

As enterprise AI architectures mature, the distinction between how an LLM reasons and how it executes actions must be rigidly enforced. In 2026, the dominant pattern for agentic workflows relies on the Model Context Protocol (MCP) to standardize tool interactions. However, the MCP specification explicitly states that tools represent arbitrary code execution and that the protocol itself cannot enforce safety principles like user consent or data isolation. Enforcement belongs to the host or the gateway.

This creates a critical architectural decision: where do we place the "guardrails"? A common mistake is to attempt to secure agent actions using Kubernetes-native tools alone. This conflates two distinct security domains. Kubernetes admission controllers (like Kyverno and Gatekeeper) protect the cluster state. Policy engines (like OPA) protect the logic of the application. To secure agent actions effectively, we must route tool calls through a policy engine that understands the context of the request, while leaving Kubernetes resource validation to its native controllers.

Why OPA is the Correct Layer for Agent Actions

Open Policy Agent (OPA) is a CNCF Graduated project that serves as a general-purpose policy engine. Unlike Kubernetes admission controllers, which only see Kubernetes API objects, OPA accepts any structured JSON input. This flexibility is what makes it ideal for evaluating LLM tool calls.

When an agent runtime or a tool gateway prepares to execute a function, it can construct a JSON payload containing the tool name, arguments, caller identity, and context. This payload is sent to OPA, typically over HTTP to /v1/data. OPA evaluates this against Rego policies and returns a structured decision. This decision is not limited to a simple boolean allow/deny; it can include structured data, such as a masked argument or a specific error message to return to the LLM.

Because OPA takes any JSON input, we can write policies that check complex logic. For example, a policy can verify that an agent is not attempting to delete production databases based on the caller’s role, or that financial calculations are within approved bounds. This is distinct from the cluster-side governance discussed in agent sprawl management, where the focus is on resource allocation rather than logic validation.

Separating Concerns: Kyverno and Gatekeeper for Cluster State

It is vital to understand what Kyverno and Gatekeeper do not do. They do not see LLM tool calls. They only see Kubernetes API requests.

Kyverno is a policy engine that acts as a Kubernetes admission controller. It can validate, mutate, generate, or clean up Kubernetes resources. It verifies container images and ensures that pods comply with security standards. If an agent tries to create a Kubernetes resource via the API, Kyverno intercepts that request. However, if the agent calls an external API or runs a script, Kyverno never sees that action.

Similarly, OPA Gatekeeper enforces CRD-based policies (ConstraintTemplates and Constraints) executed by OPA. It audits existing resources for violations and blocks new resources that do not comply. This is essential for maintaining cluster hygiene, but it is irrelevant to the logic of an agent’s tool selection.

Confusing these layers leads to fragile architectures. If you try to enforce agent logic in Gatekeeper, you are forcing Kubernetes to understand business logic it was never designed to hold. Instead, use Kyverno and Gatekeeper to ensure that the infrastructure running the agents is secure, and use OPA to ensure the agents themselves behave correctly.

Implementing the Enforcement Pattern

To implement this separation, we architect a gateway layer between the agent runtime and the external tools. This gateway is responsible for collecting telemetry and enforcing policy.

The workflow follows these steps:

  • Intercept: The agent runtime identifies a tool call that requires external execution.
  • Contextualize: The gateway constructs a JSON payload containing the tool name, arguments, and user context.
  • Evaluate: The gateway sends this payload to OPA. OPA evaluates the Rego policy against the input.
  • Act: Based on OPA’s response, the gateway either executes the tool, modifies the arguments, or rejects the call with a specific error.
  • Log: The decision and outcome are logged for observability, a topic we explored in agent observability.

This pattern ensures that policy is decoupled from the agent’s reasoning. The LLM does not need to know the security rules; the gateway enforces them transparently. This is particularly important for compliance in regulated industries, where audit trails of who did what must be maintained.

Frequently Asked Questions

Can I use Kyverno to block an LLM from calling an external API?

No. Kyverno operates at the Kubernetes API layer. It only sees requests that interact with the cluster’s resources. It cannot see or block calls made by an application to external endpoints. For that, you must use OPA or a service mesh policy engine.

Does the Model Context Protocol enforce safety?

No. The MCP specification explicitly states that it cannot enforce safety principles like user consent or tool restrictions. Enforcement belongs to the host or the gateway implementing the protocol. You must build the policy layer yourself.

What is the difference between OPA and OPA Gatekeeper?

OPA is the general-purpose policy engine that can evaluate any JSON input. OPA Gatekeeper is a Kubernetes-specific implementation that wraps OPA to enforce policies on Kubernetes resources via CRDs. Use OPA for agent actions; use Gatekeeper for cluster governance.

Where can I find the official documentation for these tools?

You can find the official documentation for Open Policy Agent at https://www.openpolicyagent.org/docs. For Gatekeeper, visit https://open-policy-agent.github.io/gatekeeper/website/docs/. For Kyverno, refer to https://kyverno.io/docs/introduction/. The MCP specification is available at https://modelcontextprotocol.io/specification/latest.
