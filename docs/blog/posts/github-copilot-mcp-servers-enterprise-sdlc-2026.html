The Policy Gate: Why MCP Servers Are Off by Default

When we discuss AI in the enterprise SDLC, the first question is always about control. GitHub Copilot’s integration with the Model Context Protocol (MCP) allows agents to interact with external tools, but this power introduces significant risk. For Copilot Business and Enterprise managed subscriptions, the MCP servers in Copilot policy is disabled by default. This is a critical distinction. It does not apply universally to all Copilot users; it specifically targets managed subscriptions where centralized governance is expected.

This default-disabled state is a safety mechanism. Before any external tool can be invoked by Copilot in an enterprise context, the admin must explicitly enable this policy. Without it, the gateway remains closed, regardless of how many MCP servers are configured in the IDE or the cloud agent. This aligns with the principle of least privilege: capability exists, but activation requires explicit administrative consent. Cloud Agent Defaults: GitHub and Playwright

Understanding the baseline configuration is essential for any enterprise architect. The Copilot cloud agent on GitHub.com comes pre-configured with two specific MCP servers: the GitHub MCP server and the Playwright MCP server. These are not optional additions; they are the default environment for cloud-based coding agents.

The GitHub MCP server allows the agent to interact with repositories, issues, and pull requests. However, it is crucial to understand that the read-only GitHub token access is the default cloud-agent configuration. This is not a universal security guarantee for all MCP usage across all IDEs or local environments. Access outside the current repository requires explicitly configuring credentials with broader access, and GitHub’s advice is to not broaden the default token’s access unless the task specifically needs it.

Playwright provides tools to read, interact with, and take screenshots of web pages. By default, it can only access web resources in the agent's own environment through localhost or 127.0.0.1. This sandboxing is vital for preventing data leakage during automated testing or UI verification tasks within the SDLC.

Enforcement: managed-settings.json vs. Registry

Once the policy is enabled, enforcement becomes the primary concern. GitHub provides two mechanisms for controlling which servers can run: the Enterprise MCP Allowlist via managed-settings.json and the GitHub MCP Registry.

GitHub recommends using managed-settings.json for allowlists. This file is generally available and allows matching by name, server URL, or stdio commands. Most enterprises store this file in a .github-private repository, though it can also be installed on users' machines with mobile device management. In contrast, the custom MCP registry is in public preview and only allows matching by name or ID, which users can potentially bypass by editing configuration files.

The evaluation order in managed-settings.json is strict and unforgiving:

  • Built-in default servers (like the built-in GitHub MCP server) are always allowed.
  • A server matching a deniedMcpServers entry is blocked immediately.
  • If allowedMcpServers is present, a server that matches no entry is blocked.
  • A server whose URL or command contains an unresolved variable is blocked.
  • A malformed list is treated as an empty allowedMcpServers list, which blocks all servers except built-in default servers.

Note that these lists do not apply to MCP servers defined in repository custom agent profiles. Within those limits, managed-settings.json is the enterprise-wide control; to stop servers defined in custom agent profiles, make sure the domains they need are not allowed by the organization or repository firewall.

Practical Configuration: The Allowlist Example

To illustrate how this works in practice, consider a scenario where an enterprise wants to allow GitHub's hosted MCP endpoint, the Playwright MCP server and the markitdown-mcp server, and block a filesystem server pointed at the root directory. The GitHub documentation provides a concrete example that demonstrates this logic:

{
  "allowedMcpServers": [
    { "serverUrl": "https://api.githubcopilot.com/*" },
    { "serverCommand": ["npx", "@playwright/mcp@latest"] },
    { "serverCommand": ["cmd", "/c", "uvx", "markitdown-mcp"] }
  ],
  "deniedMcpServers": [
    { "serverCommand": ["npx", "-y", "@modelcontextprotocol/server-filesystem", "/"] }
  ]
}

In this configuration, the first entry allows any server hosted under https://api.githubcopilot.com/, such as GitHub's remote MCP server, the second allows the Playwright server, and the third allows a specific command structure for markitdown-mcp. The denied list explicitly blocks the filesystem server configured to access the root filesystem. This granular control is what separates a secure enterprise SDLC from a chaotic development environment. Copilot Connectors and Registry Restrictions

It is important to distinguish between standard MCP servers and Copilot connectors. Connectors are remote MCP servers, such as Slack, Atlassian Rovo, or Sentry, where GitHub handles configuration and authentication. They are currently in public preview.

Connectors are allowed or blocked with serverUrl entries in the allowlist. With no allowedMcpServers list, they are allowed unless a deniedMcpServers entry matches. With an allowlist, they are blocked unless their URL matches an entry. Furthermore, setting access to 'Registry only' means users cannot use Copilot connectors. Because connectors are in public preview, the 'Editor preview features' policy must also be enabled for them to function.

Frequently Asked Questions

Does the 'MCP servers in Copilot' policy apply to all Copilot users?

No. The policy specifically applies to Copilot Business and Enterprise managed subscriptions. It is disabled by default for these managed plans to ensure enterprises can review and enable MCP capabilities intentionally.

Is read-only GitHub MCP access a universal security guarantee?

No. Read-only GitHub token access is the default configuration specifically for the Copilot cloud agent. It is not a universal security guarantee for all MCP usage. Local IDEs or custom configurations may have different permission scopes.

Can I bypass the MCP Registry by editing local files?

Yes. The GitHub MCP Registry is in public preview and allows matching only by name or ID. Users can potentially bypass registry restrictions by editing local configuration files to define their own servers, which is why GitHub recommends using managed-settings.json for stricter enforcement.

How do deniedMcpServers interact with allowedMcpServers?

The evaluation order prioritizes the denied list. If a server matches a deniedMcpServers entry, it is blocked immediately, even if it also matches an entry in the allowedMcpServers list. This ensures that explicit denials cannot be overridden by broad allowlists.
