The Supply Chain Reality in 2026

As enterprise AI adoption matures, the boundary between "code" and "configuration" has dissolved. In 2026, an agent’s capability is not just defined by its base model, but by the external components it trusts. This trust is where the supply chain risk lies. We are no longer just reviewing source code; we are auditing instruction sets and external service contracts.

Two distinct patterns dominate the current landscape: Agent Skills and the Model Context Protocol (MCP). While both extend agent capabilities, their security profiles are fundamentally different. One is a self-contained folder of instructions and scripts; the other is a separate service exposing tools via JSON-RPC. Confusing these two leads to flawed security architectures.

Understanding Agent Skills

An Agent Skill is a folder containing a SKILL.md file. This format was originally developed by Anthropic and released as an open standard, published at agentskills.io and adopted by many agent products. It is designed to be portable and human-readable.

The structure is strict. The SKILL.md file contains YAML frontmatter with a required name (max 64 chars, lowercase letters, numbers, hyphens, matching the folder name) and description (max 1024 chars). Below the frontmatter lies Markdown instructions. Optional folders like scripts/, references/, and assets/ can be included.

Skills load by progressive disclosure: only name and description (about 100 tokens) load at startup. The full SKILL.md loads when activated, and bundled files load only when needed. The optional allowed-tools field is experimental, and the specification notes that support for it may vary between agent implementations.

When auditing a skill, you are reading instructions plus optional code that runs inside the agent's own environment. You must review every bundled script for arbitrary code execution. If a skill includes a Python script in scripts/, that script inherits the agent’s runtime privileges. A malicious or poorly written script can exfiltrate data or modify system state.

Understanding Model Context Protocol (MCP)

In contrast, MCP is an open protocol using JSON-RPC 2.0 between hosts, clients, and servers. It is not a file format; it is a communication standard. Servers offer resources, prompts, and tools, and the spec says tools represent arbitrary code execution and hosts must get explicit user consent before invoking one.

An MCP server is a separate program the agent calls. It is not bundled with the agent, and the specification defines two standard transports for reaching it. With stdio, the client launches the server as a subprocess and exchanges JSON-RPC messages over its standard input and output, so the server runs on the user’s own machine; the MCP security guidance warns that such servers run with the same privileges as the client. With Streamable HTTP, the server operates as an independent process that can handle multiple client connections, on the same machine or a remote host.

In both cases the tool code runs in the server process, not inside the model. Therefore, an audit of an MCP server reviews its tools, auth, and host consent settings, plus how it is installed and launched (stdio) or exposed on the network (HTTP).

The risk depends on the transport. A local stdio server is code you download and execute on your own machine: the MCP security guidance lists malicious startup commands and malicious payloads inside the server as attack paths, with arbitrary code execution and data exfiltration as the result. A remote HTTP server means trusting someone else’s implementation, its authentication and the network path. Either way, if the server is compromised, the agent’s context is poisoned. If the host consent settings are weak, the agent may execute tools without proper verification.

Auditing the Supply Chain: A Practical Comparison

To secure your enterprise, you must audit both, but the methods differ. Here is a practical comparison of the audit focus areas.

Agent SkillMCP server
What it isA folder with a SKILL.md file (YAML frontmatter plus Markdown instructions) and optional scripts/, references/ and assets/ foldersA server speaking the open MCP protocol (JSON-RPC 2.0) that offers resources, prompts and tools to a host
Where it runsInside the agent’s own environment; bundled scripts run with the agent’s privilegesIn its own process: a local subprocess launched by the client (stdio) or an independent local or remote process (Streamable HTTP)
What to auditThe SKILL.md and every bundled script; validate frontmatter with skills-ref validateIts tools, auth and host consent settings; for stdio, the exact launch command; for HTTP, Origin checks, localhost binding and authentication

Agent Skills Audit Checklist

  1. Validate Frontmatter: Use the skills-ref library to validate SKILL.md frontmatter. Run skills-ref validate ./my-skill to ensure the name and description meet the spec.
  2. Review Bundled Code: Inspect every file in scripts/. Check for hardcoded credentials, network calls, or dangerous system commands.
  3. Check Dependencies: Ensure references/ and assets/ are from trusted sources. A link to an external resource can be a supply chain vector.

MCP Server Audit Checklist

  1. Tool Definitions: Review the JSON-RPC tool definitions. Are they specific? The spec says tools represent arbitrary code execution, so every tool the server exposes needs a reason to be there.
  2. Authentication and Authorization: How does the server authenticate? Is it using OAuth, API keys, or mTLS? Weak auth leads to unauthorized access.
  3. Host Consent Settings: Verify that the host requires explicit user consent before invoking tools. This is a requirement of the spec, but implementation varies.
  4. Transport and Launch: For a local stdio server, read the exact command and package the client will run, since it runs with the client’s privileges; the MCP security guidance recommends sandboxing with minimal default access to the file system and network. For a Streamable HTTP server, check that it validates the Origin header, binds only to localhost (127.0.0.1) when running locally, and authenticates every connection, as the transport spec asks.

Why This Matters for Enterprise Architecture

In enterprise environments, you cannot afford to trust every skill and server blindly. You need a governance model. This is where concepts like agent memory architecture and agentic command centers come into play. Just as you manage infrastructure as code, you must manage agent skills and MCP connections as code.

For more on managing complex agent ecosystems, see my post on Agent Sprawl Is the New Cloud Sprawl: How to Build an Agentic Command Center in 2026. You cannot audit what you cannot see. Centralized visibility is key to supply chain security.

Similarly, understanding how agents handle long-term memory is crucial. If an agent skill modifies memory, you need to ensure that modification is auditable. Read more about this in Agent Memory Architectures: Beyond Stuffing the Context Window.

The Hybrid Approach

Most enterprise agents will use both. A skill might invoke an MCP server. For example, a financial-audit skill might contain instructions to query a banking-api MCP server. In this case, you must audit both the skill’s instructions and the server’s tools.

The skill’s SKILL.md might define the prompt template, while the MCP server provides the actual data. If the skill instructs the agent to call a tool with a specific parameter, and the server executes it, you have a chain of trust. A break in either link compromises the system.

Best Practices for 2026

  1. Treat Skills as Code: Version control your SKILL.md files. Review changes in pull requests. Do not allow unreviewed skills in production.
  2. Minimize MCP Exposure: Only expose MCP servers that are necessary. Use allowlists for tools. Restrict network access.
  3. Validate Continuously: Use tools like skills-ref in your CI/CD pipeline. Fail builds if validation fails.
  4. Monitor Execution: Log all tool invocations from MCP servers. Log all script executions from skills. Anomaly detection is critical.
  5. Educate Teams: Developers must understand the difference between a skill and an MCP server. Training is the first line of defense.

Frequently Asked Questions

What is the primary difference between an Agent Skill and an MCP server?

An Agent Skill is a self-contained folder of instructions and optional code that runs inside the agent’s environment. An MCP server is a separate service that the agent calls via JSON-RPC. The audit of a skill reads its SKILL.md and bundled scripts, while an audit of an MCP server reviews its tools, auth, and host consent settings.

How do skills load in an agent?

Skills load by progressive disclosure. Only the name and description (about 100 tokens) load at startup. The full SKILL.md loads when activated, and bundled files load only when needed.

Is the allowed-tools field in Agent Skills secure?

The specification marks the optional allowed-tools field as experimental, and support for it may vary between agent implementations. Do not make it your only control; also rely on the agent host’s configuration and explicit user consent mechanisms for tool invocation.

How do I validate an Agent Skill?

You can use the skills-ref library. Run the command skills-ref validate ./my-skill to check that the SKILL.md frontmatter meets the specification requirements, including the name format and description length.
