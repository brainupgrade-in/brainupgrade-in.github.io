Zero-Downtime Kubernetes Upgrades: A Runbook That Works

A pragmatic, battle-tested guide to upgrading Kubernetes control planes and nodes without service interruption.

Rajesh Gheware September 9, 2026

Key Takeaways

  • 1. Always upgrade the control plane first, then drain and upgrade worker nodes in parallel.
  • 2. Use pod disruption budgets to ensure availability during rolling updates.
  • 3. Test upgrades in a staging environment that mirrors production topology before touching production.
  • 4. Monitor key metrics like API server latency and node readiness during the upgrade window.
  • 5. Have a documented rollback plan ready before initiating any upgrade steps.

The Reality of Zero-Downtime Upgrades

I’ve spent 25 years in the trenches of high-frequency trading and enterprise banking infrastructure. In those environments, "downtime" isn't just an inconvenience; it’s a direct hit to the bottom line and a breach of trust. When I talk about a kubernetes upgrade zero downtime runbook, I’m not talking about theoretical perfection. I’m talking about a practical, step-by-step process that has survived the chaos of real-world production environments.

Many engineers treat Kubernetes upgrades as an afterthought, running them on a whim. This is a mistake. A Kubernetes upgrade involves two distinct phases: the control plane (API server, etcd, scheduler, controller-manager) and the worker nodes. Each has its own risks. The control plane upgrade affects the cluster’s ability to manage workloads, while node upgrades affect the actual execution of those workloads. To achieve zero downtime, you must orchestrate these phases with surgical precision.

The goal is not just to keep the cluster running, but to ensure that your applications remain available to users. This means managing pod evictions, handling network policies, and ensuring that your monitoring and logging stacks survive the transition. If you are not careful, you can easily create a situation where your cluster is "up" but your services are unreachable.

Pre-Upgrade Strategy and Preparation

Before you even touch a command line, you need a solid plan. The most common mistake I see is jumping straight into the upgrade without validating the current state. Here is what you need to do first:

  • Verify Cluster Health: Run `kubectl get nodes` and `kubectl get pods --all-namespaces`. Ensure all nodes are in a Ready state and no pods are in a CrashLoopBackOff or Error state. If you start an upgrade with existing issues, you will only amplify them.
  • Backup etcd: This is non-negotiable. Use `etcdctl snapshot save` to create a backup of your etcd database. Store this backup in a secure, off-cluster location. If the control plane upgrade fails, this is your only way to recover.
  • Review Pod Disruption Budgets (PDBs): Ensure your critical applications have PDBs defined. A PDB ensures that a minimum number of pods remain available during voluntary disruptions, such as node drains. Without PDBs, Kubernetes might evict all pods of a critical service simultaneously during an upgrade.
  • Check Compatibility: Review the release notes for your target Kubernetes version. Pay close attention to deprecations and breaking changes in API versions, especially for custom resources and operators.

This preparation phase is often overlooked, but it is the difference between a smooth upgrade and a firefight. By ensuring your cluster is healthy and backed up, you reduce the risk of catastrophic failure. Executing the Control Plane Upgrade

The control plane upgrade is the first step. Unlike worker nodes, the control plane components are stateful and interdependent. Upgrading them out of order can lead to cluster instability. The standard procedure is to upgrade the components in this order: API Server, then etcd, then controller-manager, and finally the scheduler.

However, most modern Kubernetes distributions (like EKS, GKE, or managed Kubeadm clusters) handle this orchestration for you. If you are managing a bare-metal or on-premises cluster, you need to be more explicit. Here is a typical workflow:

  1. Upgrade the API Server: This is the entry point for all cluster communication. Ensure the new API server is healthy and can communicate with etcd.
  2. Upgrade etcd: This is the source of truth for your cluster state. Upgrade etcd members one by one, ensuring quorum is maintained at all times.
  3. Upgrade Controller Manager and Scheduler: These components manage the desired state of the cluster. Upgrade them after the API server and etcd are stable.

During this process, monitor the API server’s latency and error rates. If you see a spike in 5xx errors, pause the upgrade and investigate. It is better to delay the upgrade than to force it and risk cluster corruption. Remember, the control plane is the brain of your cluster. If it’s confused, nothing else matters.

Upgrading Worker Nodes with Zero Downtime

Once the control plane is stable, it’s time to tackle the worker nodes. This is where the "zero downtime" promise is truly tested. You cannot upgrade all nodes at once; you must do it in a rolling fashion. The key here is to drain nodes one at a time, allowing pods to reschedule on other healthy nodes.

Here is the step-by-step process for a zero-downtime node upgrade:

  • Label Nodes for Staggered Upgrades: If you have a large cluster, label nodes by availability zone or rack. This allows you to upgrade nodes in one zone at a time, ensuring that you always have capacity in other zones.
  • Drain the Node: Use `kubectl drain --ignore-daemonsets --delete-emptydir-data`. This command cordons the node and evicts all non-daemonset pods. The PDBs you configured earlier will prevent the eviction of critical pods if it would violate the minimum availability threshold.
  • Upgrade the Node: Perform the OS and Kubernetes component upgrades on the node. This might involve a reboot, depending on your setup.
  • Uncordon and Verify: Once the upgrade is complete, uncordon the node with `kubectl uncordon ` and verify that it is ready and that pods are scheduling on it.

This process can be tedious if done manually for a large cluster. This is where automation shines. I recommend using tools like AI-Powered GitOps Kubernetes Automation to orchestrate these upgrades. By defining your upgrade process as code, you can ensure consistency and repeatability across all environments.

Post-Upgrade Validation and Rollback

After the upgrade is complete, you must validate that everything is working as expected. This is not just about checking if the nodes are ready; it’s about ensuring that your applications are performing correctly. Monitor your key metrics, such as request latency, error rates, and throughput. If you see any degradation, investigate immediately.

If the upgrade fails or introduces new issues, you need a rollback plan. For the control plane, this usually involves restoring from the etcd backup. For worker nodes, it involves reverting the node images and configurations. The key is to have this plan documented and tested before you start the upgrade. Frequently Asked Questions

How long does a zero-downtime Kubernetes upgrade take?

The duration depends on the size of your cluster and the complexity of your applications. For a small cluster with 10 nodes, the process might take 1-2 hours. For a large enterprise cluster with hundreds of nodes, it could take several hours or even a full day. The key is to plan for the worst-case scenario and schedule the upgrade during a maintenance window.

Can I upgrade Kubernetes without using PDBs?

Technically, yes, but it is highly discouraged. Without PDBs, Kubernetes might evict all pods of a critical service simultaneously, leading to downtime. PDBs ensure that a minimum number of replicas remain available during voluntary disruptions, such as node drains. They are essential for achieving zero downtime.

What happens if the control plane upgrade fails?

If the control plane upgrade fails, you will likely need to restore from an etcd backup. This is why backing up etcd before the upgrade is critical. If you do not have a backup, you may need to rebuild the cluster from scratch, which is a significant outage. Always test your backup and restore procedures before attempting an upgrade.

Do I need to upgrade all nodes at the same time?

No, and you should never do that. Upgrading all nodes simultaneously can lead to a complete loss of availability if there are not enough nodes to reschedule pods. Always upgrade nodes in a rolling fashion, one at a time or in small batches, to ensure that your applications remain available throughout the process.
